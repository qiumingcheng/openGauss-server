# 原生湖代码检视与修复报告

日期：2026-11-28（二轮复检）

仓库：`qiumingcheng/openGauss-server` 的 `codex/migrate-native-lake`

检视对象：当前工作树中的原生湖模块、相关内核改动和 MERGE 接入路径

## 结论

上一版报告把 5.6 万行代码压缩成了一个已复现缺陷和若干风险项，结论不充分。本轮按模块、调用链、输入边界和动态 SQL 重新检查，新增复现 3 个确定的行为缺陷。连同 MERGE 接入缺陷，当前共确认 4 个缺陷，其中 3 个已在本地修复并完成动态复测，MERGE 接入修复已提交。版本门错误文本也已补齐。

缺陷出现在 MERGE 的接入层。原实现只检查外表是否提供 `AddForeignUpdateTargets` 回调，就把任意 FDW 外表放行到 MERGE。`postgres_fdw` 虽然提供该回调，但它的 `PlanForeignModify` 没有实现 MERGE，最终会在执行计划阶段抛出内部错误 `unexpected operation: 5`。修复后，MERGE 只允许原生湖外表进入完整的规划器和执行器契约，通用外表在解析阶段返回明确的不支持错误。

新增缺陷集中在外部路径安全边界和 JSON schema 推断。隐藏文件及隐藏目录此前可以通过外部路径校验，精确名称 `_adt` 也绕过了敏感后缀拒绝，非法日期 `2024-02-31` 会被推断为 `date`。这些问题已经用运行中的 Debug 实例复现，修复后再次验证了拒绝和合法输入行为。

原生湖核心代码结构完整，逻辑行 locator、事务私有版本、快照发布、行锁、EPQ 重检和外部 SDK 边界都有明确的接口分层。当前源码不能据此认定所有功能已经完成生产验收。部分索引、自动 flush、远端存储、物理 GC、RAC、文件来源 DML、文件采样和长稳能力在仓内文档中仍被明确标记为候选或待验收。下面把代码缺陷、性能隐患、测试缺口和能力缺口分开列出，避免把“没有发现新 bug”和“已经完成验收”混为一谈。

## 确定缺陷及修复

### 缺陷一  通用 FDW MERGE 被错误放行

问题位置在 MERGE 解析阶段和外表 junk 身份列处理阶段。

修复前，`parse_merge.cpp` 用 `AddForeignUpdateTargets != NULL` 作为外表准入条件。这个条件只能说明 FDW 能追加更新目标列，不能证明 FDW 实现了 MERGE 的计划和执行回调。`postgres_fdw` 因此被错误放行，后续执行到它的 `PlanForeignModify` 默认分支。

复现步骤使用 loopback `postgres_fdw` 外表和当前隔离实例。

```sql
MERGE INTO merge_fdw_repro.ft AS t
USING (VALUES (1, 'new'), (2, 'inserted')) AS s(id, val)
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET val = s.val
WHEN NOT MATCHED THEN INSERT (id, val) VALUES (s.id, s.val);
```

修复前结果如下。

```text
ERROR: unexpected operation: 5
```

修复后，`parse_merge.cpp` 只用 `LakeIsNativeForeignRelation(targetrel)` 允许原生湖外表进入该路径。`execJunk.cpp` 保留原生湖 locator，并对兼容的外表身份列提供防御性 `ctid` 回退。相同 SQL 现在在解析阶段返回如下错误。

```text
ERROR: Target relation type is not supported for MERGE INTO
```

远端 loopback 目标表保持原值 `1|old`，没有发生误写。

修改位置如下。

- [`parse_merge.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/src/common/backend/parser/parse_merge.cpp:820)
- [`execJunk.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/src/gausskernel/runtime/executor/execJunk.cpp:282)

### 原生湖 MERGE 定向结果

基础场景成功返回 `MERGE 2`，匹配行更新为 11，未匹配行插入为 30。带 `WHERE` 的 matched action 成功执行。重复源行命中同一持久逻辑行时返回 `MERGE command cannot affect a native lake row a second time`。重复源行命中同一事务内刚插入的行时也返回同一基数冲突。

并发场景由会话 A 先更新并持有逻辑行锁，之后会话 B 执行 MERGE。A 提交后，B 成功完成 `MERGE 1`，最终值为 500。该结果验证了 native lake 的 row-lock 和 EPQ 重检路径，未出现空身份指针或错误更新。

### 缺陷三  外部路径接受隐藏文件和隐藏目录

问题位置在 `lake_external_path.cpp` 的路径分段和 basename 校验。原实现只拒绝精确的 `.` 和 `..`，注释写的是拒绝隐藏 dot segment，实际却允许 `.og_lake_hidden_repro.csv` 和 `.og_lake_hidden_dir/file.csv`。这会让不应进入外部数据入口的隐藏路径通过格式描述接口。

复现输入如下。

```text
/tmp/.og_lake_hidden_repro.csv
/tmp/.og_lake_hidden_dir/file.csv
```

修复前，两个路径都返回了正常的 `id|bigint` 和 `name|text` 描述。修复把所有以点开头的路径段纳入拒绝条件，并对 basename 做同样的保护。修复后，basename 返回 `invalid or disallowed external relative file path`，隐藏目录返回 `external lake root contains invalid or dot path components`。`/tmp/og_lake_normal_repro.csv` 仍返回两列正常描述。

修改位置为 [`lake_external_path.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/contrib/og_lake/lake_external_path.cpp:30) 和 [`lake_external_path.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/contrib/og_lake/lake_external_path.cpp:199)。

### 缺陷四  精确 `_adt` 文件名绕过敏感后缀拒绝

问题位置是 `LakeEndsWithInsensitive`。原条件使用 `vlen > slen`，所以字符串长度刚好等于后缀时不会比较。`foo_adt` 能被拒绝，精确 basename `_adt` 却可以通过。

复现前，`describe_external_path('/tmp/_adt', 'csv', true, ',')` 返回正常列描述，`foo_adt`、`openssl.cnf`、`foo.key.cipher` 和 `foo.key.rand` 已被拒绝。修复把条件改为 `vlen >= slen`。复测后 `_adt` 以及大小写和前缀变体均返回 `invalid or disallowed external relative file path`，普通 CSV 仍可描述。

修改位置为 [`lake_external_path.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/contrib/og_lake/lake_external_path.cpp:52)。

### 缺陷五  JSON 日期推断接受不存在日期

问题位置是 `LakeJsonIsDateStr`。原实现只校验月份在 1 到 12、日期在 1 到 31，没有按月份和闰年校验日历边界。`2024-02-31` 因此会被推断为 `date`。

复现 SQL 读取一行 JSONL。

```sql
select * from og_lake.describe_external_path('/tmp/og_lake_bad_date.jsonl', 'json');
```

修复加入每月天数和 Gregorian 闰年规则。复测结果为 `2024-02-29` 推断为 `date`，`2023-02-29`、`2024-04-31` 和 `2024-02-31` 推断为 `text`，`2024-04-30` 推断为 `date`。这避免 schema inference 把无效业务日期升级成错误的数据库日期类型。

修改位置为 [`lake_copy.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/contrib/og_lake/lake_copy.cpp:1465)。

## 已确认的性能隐患

以下项目是代码和执行路径可以直接确认的性能风险，不是本轮复现出的数据正确性缺陷。

1. MERGE、UPDATE 和 DELETE 的每条候选行都会经过逻辑 row-head 锁。`LakeLockLogicalRow` 内部需要查询绑定、确保 row-head 存在并执行 `SELECT ... FOR UPDATE`。大批量 MERGE 的锁管理成本会随匹配行数增长，热点逻辑行会产生锁等待。
2. RC 冲突重检通过 `LakeTxnResolveLatestRow` 打开新的读取视图，再扫描可见 inline/file 版本寻找指定 `row_id`。在大表上，冲突行的重检可能退化为按文件和版本数量线性扫描。该路径保证了正确性，但没有索引化的逻辑 row ID 定位结构。
3. `LakeMetadataQuery` 已有只读 SPI 计划缓存，但每个绑定、快照和行锁路径仍可能进行多次元数据查询。MERGE 大批量执行时，元数据 SPI 和权限范围切换会叠加到每行成本上。
4. 文件索引和 ANN 路径在 coverage 不完整、对象版本变化或预算不足时保留完整扫描回退。它优先保证结果正确，但在混合 indexed/uncovered 文件上可能出现延迟和 I/O 突增。仓内文档也明确写出了这个行为。
5. 写集合预算、哈希表、临时 tuple 和 provider buffer 的总 RSS 不由单一 64 MiB 写集合上限完全约束。仓内设计文档已经把 allocator、hash 和外部 provider 的额外占用列为后续验收项。

### P-01 的处理方案

当前不直接改成无锁或弱锁路径。row-head 是逻辑行并发控制的正确性基础，贸然减少锁会改变 MERGE 的冲突语义。

需要新增四组基线。

- 1 万、10 万和 100 万行的单事务 MERGE
- 多会话更新同一逻辑行的热点冲突
- 多会话更新互不相交逻辑行的并行度
- 使用和不使用 row-head 缓存的 SPI 次数、锁等待和峰值 RSS

基线确认锁查询是主要成本后，再考虑在 statement 级缓存绑定到 row-head relation OID，或者为同一批候选行增加受控批量锁定。修改后必须复跑重复匹配、并发更新、回滚和取消场景。

### P-02 的处理方案

当前 `LakeTxnResolveLatestRow` 的完整可见性扫描必须保留，它是冲突时的正确性兜底。后续可以增加受保护的 `row_id` 到当前物理版本定位结构，并在定位结果失效时回退到现有全扫描。新结构需要绑定 snapshot、source version、file id 和 physical position，不能只缓存文件位置。

修改前后需要对比相同数据集下的冲突延迟、扫描文件数、读取字节数和最终结果。没有这些数据前不修改现有冲突路径。

### P-03 的处理方案

完整扫描回退当前不需要修改。它保证 coverage 缺失、对象版本变化、索引损坏和预算不足时仍返回正确结果。后续工作放在覆盖率建设、对象版本校验的缓存和 planner 成本模型，禁止通过跳过回退来换取表面性能。

### P-04 的处理方案

需要把写集合、statement hash、临时 tuple、Arrow buffer 和 provider candidate 统一纳入可观测预算。第一步增加压力用例和内存计数，第二步再决定拒绝、缩批或 spill。当前没有证据支持直接调大 64 MiB 上限，不能用提高阈值掩盖 RSS 不可控问题。

建议后续用大批量 MERGE、热点更新、冲突重检和 indexed/uncovered 混合文件分别采集 `EXPLAIN ANALYZE`、SPI 调用数、row-head 锁等待、文件读取字节数和峰值 RSS。当前没有足够的新环境基准支持给出收益百分比。

## 设计质量和 Clean Code 评价

### 做得较好的部分

- 使用明确的逻辑 locator 传递 row ID、源版本和物理位置，避免把 heap `ctid` 当作湖表永久身份。
- native lake 的修改状态位于 query memory context，prepared locator、EPQ 视图、statement 去重表和事务发布状态分开管理。
- SDK provider 使用 ABI、capability 和 size 检查，旧版本拒绝不支持的扩展字段，读取路径保留校验和取消传播。
- 事务发布、保存点、候选文件关闭和异常清理大量采用 `PG_TRY`、`PG_CATCH` 和显式资源释放，错误不会被静默吞掉。
- 对远端 URL、符号链接、路径穿越、外部对象版本和不完整 coverage 采用拒绝或完整扫描策略，边界行为明确。

### 需要继续改善的部分

- 代码风格不一致。部分新增文件使用紧凑的单行多语句和多层条件表达式，增加审查和后续调试成本。当前没有进行全仓格式化，避免制造与功能无关的大量 diff。
- `LakeRequireWriteVersion` 的错误文本在修复前只提到 INSERT、UPDATE 和 DELETE，MERGE 走同一版本门时错误信息不完整。本轮已经补充 MERGE，版本判断逻辑没有改变。
- `lake_external_path.cpp` 在遍历 `safe_data_path` 时为每个候选根分配字符串，只有最长匹配根被保留，其余候选根留在当前内存上下文。它通常随语句或事务上下文回收，尚未证明为持续性泄漏。本轮没有在需要重启才能设置的 `safe_data_path` 环境上做内存增长复现，因此没有擅自修改该段资源管理代码。
- 解析器、重写器、执行器和扩展模块之间通过多个全局入口函数耦合。现有接口有版本门和计划私有版本保护，后续仍应补充统一的 capability contract，减少同一能力在多个阶段重复判断。
- 部分功能状态主要由版本字符串和大量条件门控制。升级路径正确性依赖精确安装 SQL 版本，测试矩阵应把版本门、计划私有版本和 provider ABI 作为同一兼容性维度持续验证。

### C-01 的处理方案

这个问题目前仍是静态发现，不能直接写成已确认的泄漏。需要在启动参数中配置两个以上 `safe_data_path`，在一个长事务内重复调用路径授权接口，记录事务内存上下文和授权结果。只有复现内存持续增长后才修改释放逻辑，并补同一组路径边界测试。

### C-02 的处理方案

这是确定的错误信息缺失，版本判断本身没有问题。本轮已将错误文本补为包含 MERGE 的版本门说明，并完成增量编译。当前工作区缺少匹配旧版扩展的 SQL 夹具，因此旧版本拒绝路径未做动态重放，后续发布验收需要补做。

### C-03 的处理方案

不做全仓格式化。全仓格式化会产生大量无关 diff，降低后续缺陷定位能力。以后修改某个文件时只整理相邻代码，保留原有功能变更边界。

### C-04 的处理方案

当前 `version()` 的基线值会误导定位。它属于构建身份问题，不应通过手工修改字符串解决。发布前应让构建系统写入真实源码 commit，并在 build receipt、安装目录和 `version()` 三处做一致性检查。本轮不把版本体系改动和 MERGE 修复混在一起。

## MERGE 的明确边界

当前 fork 的语法只定义了 `WHEN MATCHED THEN UPDATE` 和 `WHEN NOT MATCHED THEN INSERT`。`WHEN MATCHED THEN DELETE` 在 `gram.y` 中没有产生式，执行器也只处理 `CMD_INSERT` 和 `CMD_UPDATE`。这是当前 MERGE 语法和通用执行器的限制，不是本轮 native lake 接入遗漏。

当前实现还明确拒绝分区父表 MERGE、修改 CTE、多目标 MERGE、UPSERT 组合和不满足 row-lock/READ COMMITTED 条件的执行。相关拒绝应继续保留，直到对应 planner、locator、EPQ、发布和回滚契约具备独立测试。
