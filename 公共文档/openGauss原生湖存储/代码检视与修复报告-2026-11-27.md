# 原生湖代码检视与修复报告

日期：2026-11-27

检视对象：当前工作树中的原生湖模块、相关内核改动和 MERGE 接入路径

## 结论

本轮发现并复现 1 个确定缺陷，已完成修复。

缺陷出现在 MERGE 的接入层。原实现只检查外表是否提供 `AddForeignUpdateTargets` 回调，就把任意 FDW 外表放行到 MERGE。`postgres_fdw` 虽然提供该回调，但它的 `PlanForeignModify` 没有实现 MERGE，最终会在执行计划阶段抛出内部错误 `unexpected operation: 5`。修复后，MERGE 只允许原生湖外表进入完整的规划器和执行器契约，通用外表在解析阶段返回明确的不支持错误。

原生湖核心代码结构完整，逻辑行 locator、事务私有版本、快照发布、行锁、EPQ 重检和外部 SDK 边界都有明确的接口分层。当前源码不能据此认定所有功能已经完成生产验收。部分索引、自动 flush、远端存储、物理 GC、RAC 和长稳能力在仓内文档中仍被明确标记为候选或待验收。

## 确定缺陷及修复

### 缺陷一  通用 FDW MERGE 被错误放行

问题位置在 MERGE 解析阶段和外表 junk 身份列处理阶段。

修复前，`parse_merge.cpp` 用 `AddForeignUpdateTargets != NULL` 作为外表准入条件。这个条件只能说明 FDW 能追加更新目标列，不能证明 FDW 实现了 MERGE 的计划和执行回调。`postgres_fdw` 因此被错误放行，后续执行到它的 `PlanForeignModify` 默认分支。

复现步骤使用 loopback `postgres_fdw` 外表和当前隔离实例。

```sql
MERGE INTO merge_fdw_repro.ft AS t
USING (VALUES (1, 'new'), (2, 'inserted')) AS s(id, val)
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET val = s.val
WHEN NOT MATCHED THEN INSERT (id, val) VALUES (s.id, s.val);
```

修复前结果如下。

```text
ERROR: unexpected operation: 5
```

修复后，`parse_merge.cpp` 只用 `LakeIsNativeForeignRelation(targetrel)` 允许原生湖外表进入该路径。`execJunk.cpp` 保留原生湖 locator，并对兼容的外表身份列提供防御性 `ctid` 回退。相同 SQL 现在在解析阶段返回如下错误。

```text
ERROR: Target relation type is not supported for MERGE INTO
```

远端 loopback 目标表保持原值 `1|old`，没有发生误写。

- [`execJunk.cpp`](/data/qiumc/code/cpp/opengauss-native-lake/src/gausskernel/runtime/executor/execJunk.cpp:282)

### 原生湖 MERGE 定向结果

基础场景成功返回 `MERGE 2`，匹配行更新为 11，未匹配行插入为 30。带 `WHERE` 的 matched action 成功执行。重复源行命中同一持久逻辑行时返回 `MERGE command cannot affect a native lake row a second time`。重复源行命中同一事务内刚插入的行时也返回同一基数冲突。

并发场景由会话 A 先更新并持有逻辑行锁，之后会话 B 执行 MERGE。A 提交后，B 成功完成 `MERGE 1`，最终值为 500。该结果验证了 native lake 的 row-lock 和 EPQ 重检路径，未出现空身份指针或错误更新。

## 已确认的性能隐患

以下项目是代码和执行路径可以直接确认的性能风险，不是本轮复现出的数据正确性缺陷。

1. MERGE、UPDATE 和 DELETE 的每条候选行都会经过逻辑 row-head 锁。`LakeLockLogicalRow` 内部需要查询绑定、确保 row-head 存在并执行 `SELECT ... FOR UPDATE`。大批量 MERGE 的锁管理成本会随匹配行数增长，热点逻辑行会产生锁等待。
2. RC 冲突重检通过 `LakeTxnResolveLatestRow` 打开新的读取视图，再扫描可见 inline/file 版本寻找指定 `row_id`。在大表上，冲突行的重检可能退化为按文件和版本数量线性扫描。该路径保证了正确性，但没有索引化的逻辑 row ID 定位结构。
3. `LakeMetadataQuery` 已有只读 SPI 计划缓存，但每个绑定、快照和行锁路径仍可能进行多次元数据查询。MERGE 大批量执行时，元数据 SPI 和权限范围切换会叠加到每行成本上。
4. 文件索引和 ANN 路径在 coverage 不完整、对象版本变化或预算不足时保留完整扫描回退。它优先保证结果正确，但在混合 indexed/uncovered 文件上可能出现延迟和 I/O 突增。仓内文档也明确写出了这个行为。
5. 写集合预算、哈希表、临时 tuple 和 provider buffer 的总 RSS 不由单一 64 MiB 写集合上限完全约束。仓内设计文档已经把 allocator、hash 和外部 provider 的额外占用列为后续验收项。

建议后续用大批量 MERGE、热点更新、冲突重检和 indexed/uncovered 混合文件分别采集 `EXPLAIN ANALYZE`、SPI 调用数、row-head 锁等待、文件读取字节数和峰值 RSS。当前没有足够的新环境基准支持给出收益百分比。

## 设计质量和 Clean Code 评价

### 做得较好的部分

- 使用明确的逻辑 locator 传递 row ID、源版本和物理位置，避免把 heap `ctid` 当作湖表永久身份。
- native lake 的修改状态位于 query memory context，prepared locator、EPQ 视图、statement 去重表和事务发布状态分开管理。
- SDK provider 使用 ABI、capability 和 size 检查，旧版本拒绝不支持的扩展字段，读取路径保留校验和取消传播。
- 事务发布、保存点、候选文件关闭和异常清理大量采用 `PG_TRY`、`PG_CATCH` 和显式资源释放，错误不会被静默吞掉。
- 对远端 URL、符号链接、路径穿越、外部对象版本和不完整 coverage 采用拒绝或完整扫描策略，边界行为明确。

### 需要继续改善的部分

- 代码风格不一致。部分新增文件使用紧凑的单行多语句和多层条件表达式，增加审查和后续调试成本。当前没有进行全仓格式化，避免制造与功能无关的大量 diff。
- `LakeRequireWriteVersion` 的错误文本仍只提到 INSERT、UPDATE 和 DELETE，MERGE 走同一版本门时错误信息不完整。这是可读性问题，不影响当前判定。
- `lake_external_path.cpp` 在遍历 `safe_data_path` 时为每个候选根分配字符串，只有最长匹配根被保留，其余候选根留在当前内存上下文。它通常随语句或事务上下文回收，尚未证明为持续性泄漏。本轮没有在需要重启才能设置的 `safe_data_path` 环境上做内存增长复现，因此没有擅自修改该段资源管理代码。
- 解析器、重写器、执行器和扩展模块之间通过多个全局入口函数耦合。现有接口有版本门和计划私有版本保护，后续仍应补充统一的 capability contract，减少同一能力在多个阶段重复判断。
- 部分功能状态主要由版本字符串和大量条件门控制。升级路径正确性依赖精确安装 SQL 版本，测试矩阵应把版本门、计划私有版本和 provider ABI 作为同一兼容性维度持续验证。

## MERGE 的明确边界

当前 fork 的语法只定义了 `WHEN MATCHED THEN UPDATE` 和 `WHEN NOT MATCHED THEN INSERT`。`WHEN MATCHED THEN DELETE` 在 `gram.y` 中没有产生式，执行器也只处理 `CMD_INSERT` 和 `CMD_UPDATE`。这是当前 MERGE 语法和通用执行器的限制，不是本轮 native lake 接入遗漏。

当前实现还明确拒绝分区父表 MERGE、修改 CTE、多目标 MERGE、UPSERT 组合和不满足 row-lock/READ COMMITTED 条件的执行。相关拒绝应继续保留，直到对应 planner、locator、EPQ、发布和回滚契约具备独立测试。
